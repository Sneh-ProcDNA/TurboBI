# Project overview

Qlik Sense (QVF) → Power BI Project (PBIP) converter. Code lives under `qlik_to_pbi/` (Python package, ~12k LOC, 20 modules). Entry point: `python -m qlik_to_pbi`.

## Key invariants the architecture rests on

- The engine-current schema (`GetTablesAndKeys` with `qSyntheticMode=false`) is the **authoritative** data-model source. The `loadmodel---loadmodel.json` snapshot is frozen at the last reload and routinely diverges. Field-list code MUST prefer engine schema when available; loadmodel is the fallback for non-engine paths.
- **Engine field tags drive column types**, not the CSV sniffer. `csv_schema.type_from_qlik_tags` maps `$integer` / `$numeric` / `$date` / `$timestamp` / `$text` to TMDL dataType. Robust against CSV misalignment AND missing data files. CSV sniffer is fallback only.
- The Qlik load script's autogenerated section RENAMEs synthetic keys (`[HCP_ID] AS [From_HCP_ID-HCP_ID]`) and DROPs source columns. `script_parser.parse_field_renames` recovers per-table rename maps; downstream code uses these to label TMDL columns with friendlier original names and to translate `qk` join keys to the right per-table columns.
- The DAX translator has two stages: a legacy regex pipeline that handles the common corpus, then a v2 tokenizer (`dax_translator_v2.py`) that runs only when legacy stubs. v2 is where new function-coverage entries go (`SCALAR_1_MAP` / `SCALAR_N_MAP` / `AGG_MAP`).
- **Data extract uses hypercube only** — never `Doc.GetTableData`. Hypercube has caller-controlled column ordering (dim order = output cell order). `GetTableData.qValue[]` is in the engine's internal physical table-layout order, which disagrees with `GetTablesAndKeys.qFields` order for joined tables — producing CSVs where headers don't align with data.
- **Cloud `qlik app unbuild` does NOT export bookmarks.** The only way to recover them is `engine_unbuild._write_bookmarks` via the engine's `BookmarkList` listdef.
- **Engine inherits the QVF's saved selection state on open.** If the author saved while a bookmark was active, `GetHyperCubeData` returns rows filtered by that bookmark's selection — the CSV is a partial slice. `EngineClient.connect()` calls `Doc.ClearAll(qLockedAlso=true)` after `app_handle` is resolved so the extract reflects the full table. PBI bookmarks (which are visual-layer state) then layer their own filters on top of complete data.

**Why:** decisions through 7 conversations of feature work — building the wrong abstraction here costs days of regression chasing.

**How to apply:** When adding a new feature, ask first: "does this contradict the engine-schema-as-truth invariant, or the legacy-then-v2 translator order?" If yes, refactor through the existing extension points (`engine_schema['field_renames']`, `dax_translator_v2.SCALAR_N_MAP`, etc.) rather than adding parallel logic.
