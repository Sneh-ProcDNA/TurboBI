# Known limitations / open work

Tracked gaps as of conversation #7 (May 22 2026):

- **Composite set analysis** — RESOLVED for the common cases (multi-key, multi-value `IN`, `<>` negation, `{"*"}` wildcard, `distinct` after the set block, and `>a <b` range/date search strings with scalar date-pivot mapping). See `dax-translator-architecture.md`. Still stubbed: quarter-pivot range bounds and bounds whose inner expression doesn't translate.
- **Aggregation over an expression** — RESOLVED (2026-06). `SUM`/`AVERAGE`/`MIN`/`MAX`/`DISTINCTCOUNT` of an expression (not a bare column) now promote to the iterator (`SUMX`…) or `CALCULATE(DISTINCTCOUNT(col), FILTER(…))` form via `_finalize_dax`, applied to both the legacy and v2 result. Fixes the refresh error *"The SUM/DISTINCTCOUNT function only accepts a column reference as an argument"* (the v2 set-analysis path previously skipped the legacy promotion). See `dax-translator-architecture.md`.
- **Bare variable reference** — RESOLVED (2026-06). A bare `varName` (not `$(varName)`) now resolves to the variable's materialised measure ref / inline scalar instead of a bogus `'home'[varName]` column. Fixes the refresh error *"Column 'varName' … cannot be found"*.
- **`AGGR(...)`** — stubbed.
- **Variable expansion** — `$(var)` and `$(=var)` both expand to the body; Qlik comments are stripped first (a trailing `//` comment in a variable body used to swallow the wrapper's closing paren). `=If(...)` bodies still rely on the legacy/v2 translators handling the resulting expression.
- **Pivot table cell formatting** — totals, column widths, and conditional formatting on table cells aren't carried through.
- **Drill-down / hierarchies** — Qlik drill dimensions aren't mapped to PBI hierarchies.
- **Story / alternate states** — Qlik's `qStateName`-based alternate selections have no direct PBI analogue; the closest is page-level filters, currently not auto-generated.
- **Bookmark selection state** — Field selections are now CAPTURED: `engine_unbuild._capture_bookmark_selections` applies each bookmark and reads the selection object (`field → values`), resolving engine-summarised "N of M" selections to explicit values via a per-field list object. These are written to `bookmarks.json` as `selections[]` and listed in the report's **Bookmarks** section. The emitted PBI `.bookmark.json` is still a name+page scaffold — encoding selections into PBI bookmark filter-state was deliberately deferred (the explorationState filter schema is finicky and a malformed bookmark fails the whole report load; not safe to ship unverified). The cloud unbuild CLI omits bookmarks entirely; we recover them via the engine's `BookmarkList` listdef in `engine_unbuild._write_bookmarks`.
- **QVD direct read** — PBI's QVD connector is preview-only; we currently stub `.qvd` sources with a note (`Source = #table({}, {})` + `Table.SelectColumns(…, MissingField.Ignore)`). Future option: shell out to a QVD-to-Parquet utility during conversion. The empty stub is **in-memory and connects to nothing**, so it loads AND refreshes cleanly with zero rows — it does NOT by itself throw an OLE DB error. (`OLE DB or ODBC error: 0x80040E4E` / "Load was cancelled by an error in loading a previous table" sprayed across many tables is almost always the **relationship-failure cascade** — see the cardinality entry below — not a per-table data-source error. PBI's `DB_E_NOTABLE` is the generic code it reports on sibling tables when one table aborts the shared refresh transaction.) To get real rows into a QVD-stub table, fetch CSVs or repoint the partition in Transform Data.
- **Relationship cardinality vs real data** — RESOLVED (2026-06). The converter emits **every relationship many-to-many, single-direction** and NEVER auto-emits a many-to-one (`_assign_relationship_cardinality`). This makes the load-fatal *"Column 'X' … contains a duplicate value … not allowed … on the one side of a many-to-one relationship"* (and its `0x80040E4E` cascade) **structurally impossible** — only a wrong many-to-one can trigger it, and the converter never emits one. It cannot reliably prove one-side uniqueness at convert time: cloud fetch is row-capped (~500 rows), so a CSV that *looks* unique may not be in the full data — which is exactly how `AggSales[AggKey]='103-10015824-roadway'` kept failing even after an earlier "prove from the CSV and upgrade" attempt. Consequences are asymmetric: a false many-to-one breaks the whole report; many-to-many merely makes a relationship "limited". `crossFilteringBehavior: oneDirection` keeps dim→fact filtering identical to M:1 for normal visuals. The interim many-to-one default regressed 5 apps (ItemMaster → ShipToAddress2 → SalesRep → MasterPlanning='' → AggSales composite key) before being abandoned. Users tighten specific relationships to M:1 in Desktop where PBI checks the real loaded data. ⚠️ Do NOT reintroduce an automatic many-to-one path. See [[tmdl-emit-rules]], bed `regression/cardinality_dupkey.py`.
- **Conditional visibility** — `qCalcCondition` expressions are recorded as notes in the conversion report but not wired as PBI filters (would need a synthesised measure).
- **Fetch-data CSV-to-table name binding** — fetched CSVs are named after their Qlik object title (e.g. `Hospital Analysis - Linechart.csv`); for tables only exposed via a chart, manual rename to `<TableAlias>.csv` is still needed. Offline `--fetch-via-engine` solves this by writing `<tableAlias>.csv` directly.

**Why:** documenting these so we don't re-investigate them as bugs.

**How to apply:** When a user reports one of these, point at the gap rather than treating it as a regression. New function-coverage entries go into `dax_translator_v2.SCALAR_N_MAP` etc. — see `dax-translator-architecture.md`.
